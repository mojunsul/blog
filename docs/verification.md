# 검증 세션 규칙

> CLAUDE.md에서 분리한 검증 세션 전용 규칙. 아래의 "Git 섹션"은 CLAUDE.md의 Git 섹션이다.

사용자가 "검증 세션"이라고 밝힌 세션은 요청마다 이슈 #N을 검증한다. "#N 설계 검증해줘"는 구현 전 설계 검증, "#N 검증해줘"는 구현 검증이다. 흐름: 설계 → 설계 검증 → 구현 → 구현 검증. 위반이 있으면 고칠 세션이 고친 뒤 다시 검증한다.

- 공통: 대상은 이슈 #N의 브랜치(이슈 본문에 적힌 브랜치, 없으면 `feat/#N-*`·`fix/#N-*`·`docs/#N-*` 등 `*/#N-*`, 못 찾거나 여럿이면 묻는다). `git fetch` 후 스크래치패드 worktree에 체크아웃해 보고(저장소 폴더의 브랜치는 바꾸지 않는다), 마치면 worktree를 삭제한다. 로컬 브랜치가 원격보다 앞서 있거나 원격에 없으면 push 전 로컬 커밋을 검증하고, 검증한 커밋 SHA와 원격 대비 상태(ahead/behind)를 결과에 적는다. 요청끼리 독립적이라 이전 검증의 결론을 끌어오지 않는다. 코드·문서를 고치지 않고, 머지·브랜치 삭제·저장소 설정 변경도 하지 않는다.
- 판정은 깐깐하게 한다: 규칙 문구뿐 아니라 취지에서 벗어나도 위반으로 분류하고, 수정 비용이 작다는 이유로 낮추지 않는다. "참고"는 어떤 규칙에도 걸리지 않는 개선 제안에만 쓴다.
- 읽기는 호출 수와 출력량을 줄인다 (요청마다 대화 전체가 다시 전송된다).
  - 관련 문서 장은 `grep -n '^#' docs/architecture.md`로 줄 범위를 찾은 뒤, 필요한 장을 한 번의 명령으로 묶어 읽는다. 장마다 따로 읽지 않는다.
  - 14장 변경 이력은 전체를 출력하지 않는다. 마지막 버전 번호와 이번 브랜치가 추가한 항목(diff에 있다)만 본다.
  - 서로 의존하지 않는 조회(이슈 본문, 브랜치 확인, diff, 관련 코드)는 한 번의 명령으로 묶거나 같은 턴에 병렬로 실행한다.
  - 외부 라이브러리 동작 확인(jar 소스 등)은 문서의 주장이 판정에 영향을 줄 때만 한다.
- 설계 검증: 이슈 #N 본문과 `origin/main...브랜치`의 `docs/architecture.md`·CLAUDE.md diff를 읽는다. 빌드·실행은 하지 않는다. 이슈 본문과 문서가 서로 어긋나면 그 자체로 위반이다. 점검 항목:
  - 이슈의 할 일·완료 조건이 모두 문서로 뒷받침되어, 구현이 문서에 없는 결정을 떠안지 않는가
  - 입력 경계(최소·최대, 빈 값, 형식 오류, 같은 키 여러 개)마다 결과(상태 코드와 ErrorCode, 또는 화면)가 정해져 있는가
  - 기존 장(5장 백엔드 규칙, 7장 API 공통 규칙, 9장 에러, 11장 프론트 등)과 CLAUDE.md 규칙에 어긋나지 않는가
  - 완료 조건마다 확인 수단(테스트 또는 화면)이 있고, 그 이슈 범위 안에서 확인할 수 있는가
  - `docs/architecture.md`를 바꿨으면 14장 변경 이력에 반영했는가
- 구현 검증: 기준(우선순위 순)은 이슈 본문 → 그 브랜치의 `docs/architecture.md` → 그 브랜치의 CLAUDE.md 규칙. `origin/main...브랜치` diff를 이슈의 할 일·완료 조건·테스트 항목과 하나씩 대조 → `./gradlew build` 직접 실행(프론트 변경 시 lint·typegen·tsc·build·test도, CI 결과는 머지 조건이라 확인하지 않는다) → "통과 / 위반(파일:줄 + 어긴 규칙·문서 위치) / 확인 못 함"으로 정리한다.
- 결과 처리
  - 위반 없음: 사용자 확인 없이 이슈에 코멘트를 남긴다. 제목은 `## 설계 검증 결과` 또는 `## 검증 결과`에 (브랜치, SHA, push 상태, 원격 대비 ahead/behind)를 붙이고, 실행한 검사와 완료 조건 확인을 한 문단으로 쓴 뒤 "위반 없음"으로 맺는다. 필요하면 `### 확인 못 함`, `### 참고`를 덧붙인다. 이어서 단계 라벨을 다음 단계로 바꾼다 (Git 섹션 '라벨').
  - 위반 있음: GitHub에는 남기지 않는다 (바로 고쳐지므로 Public 이슈에는 최종 "위반 없음"만 남긴다). 고칠 세션(설계 검증은 설계 세션, 구현 검증은 구현 세션)에 붙여 넣을 프롬프트를 사용자에게 출력한다. 프롬프트에는 이슈·브랜치·검증 SHA, 위반별 파일:줄·어긴 기준(규칙·문서 위치)·재현·고칠 방향, 마친 뒤 할 일(커밋, 재검증 요청)을 넣는다.
  - 구현 검증에서 설계 결정이 필요한 위반: 설계 세션이 대화 밖에서 읽을 수 있게 이슈에 설계 질문(현상·원인·결정할 선택지)으로 코멘트하고, 구현 세션 프롬프트에는 "설계 결정 후 반영"으로 표시한다. 구현 세션이 같은 내용을 이미 코멘트했으면 다시 남기지 않는다.
