# 검증 세션 규칙

> CLAUDE.md에서 분리한 검증 세션 전용 규칙. 아래의 "Git 섹션"은 CLAUDE.md의 Git 섹션이다.

사용자가 "검증 세션"이라고 밝힌 세션은 이슈 #N을 검증한다. "#N 설계 검증해줘"는 구현 전 설계 검증, "#N 검증해줘"는 구현 검증이다. "#N 설계 재검증해줘"·"#N 재검증해줘"는 고친 뒤 다시 하는 검증이다 (아래 '재검증'). 흐름: 설계 → 설계 검증 → 구현 → 구현 검증. 위반이 있으면 고칠 세션이 고친 뒤 다시 검증한다.

- 요청 하나에 세션 하나: 설계 검증, 구현 검증, 재검증은 각각 새 세션에서 연다. 한 세션에서 요청을 이어 하면 앞선 요청의 문서·diff가 이후 요청마다 계속 함께 전송된다. 같은 세션에서 다음 요청이 오면 막지 않고 처리하되, 결과 끝에 다음 요청은 새 세션에서 하라는 한 줄을 붙인다.

- 공통: 대상은 이슈 #N의 브랜치(이슈 본문에 적힌 브랜치, 없으면 `feat/#N-*`·`fix/#N-*`·`docs/#N-*` 등 `*/#N-*`, 못 찾거나 여럿이면 묻는다). `git fetch` 후 스크래치패드 worktree에 체크아웃해 보고(저장소 폴더의 브랜치는 바꾸지 않는다), 마치면 worktree를 삭제한다. 로컬 브랜치가 원격보다 앞서 있거나 원격에 없으면 push 전 로컬 커밋을 검증하고, 검증한 커밋 SHA와 원격 대비 상태(ahead/behind)를 결과에 적는다. 요청끼리 독립적이라 이전 검증의 결론을 끌어오지 않는다 (재검증이 읽는 범위를 줄이는 것만 아래 '재검증'에서 따로 정한다). 코드·문서를 고치지 않고, 머지·브랜치 삭제·저장소 설정 변경도 하지 않는다.
  - 읽기는 호출 수와 출력량을 줄인다 (요청마다 대화 전체가 다시 전송된다).
    - 관련 문서에 적힌 장 파일(과 추가로 읽을 장 파일)을 한 번의 명령으로 묶어 읽는다. 장마다 따로 읽지 않는다.
    - 관련 문서가 절 번호(`10-1, 10-2`)를 적었으면 그 절만 읽는다. 장 번호만 적었으면(`11장`) 장 전체를 읽는다. 파일마다 한 번에 자른다: `awk '/^### /{p=0} /^### (10-1|10-2)\. /{p=1} p' docs/architecture/10-auth-security.md`. 출력이 비면(절 번호 제목이 없는 장) 그 장 전체를 읽는다. 절만으로 판정이 모자라면 다른 절·장을 더 읽고, 읽은 곳과 이유를 결과에 적는다 (CLAUDE.md '먼저 읽을 것'과 같다).
    - 빌드·테스트(`./gradlew build`, 프론트 lint·typegen·tsc·build·test)는 출력을 스크래치패드의 로그 파일로 받고 종료 코드만 본다 (`./gradlew build > 로그 2>&1; echo exit=$?`). 성공하면 로그를 출력하지 않는다. 실패하면 로그의 끝 `tail -n 60`만 출력하고, 모자라면 오류 줄만 `grep -n`으로 더 뽑는다. 결과에는 통과나 실패 원인만 적는다.
    - 변경 이력(`docs/changelog.md`)은 관련 문서에 변경 이력이 적혀 있어도 전체를 출력하지 않는다. 마지막 버전 번호와 이번 브랜치가 추가한 항목(diff에 있다)만 본다. CLAUDE.md의 "적힌 장을 반드시 읽는다"에 대한 예외다 (변경 이력은 판정에 쓰는 규칙이 아니라 기록이라서).
    - 서로 의존하지 않는 조회(이슈 본문, 브랜치 확인, diff, 관련 코드)는 한 번의 명령으로 묶거나 같은 턴에 병렬로 실행한다.
    - 외부 라이브러리 동작 확인(jar 소스 등)은 문서의 주장이 판정에 영향을 줄 때만 한다.
- 판정은 깐깐하게 한다: 규칙 문구뿐 아니라 취지에서 벗어나도 위반으로 분류하고, 수정 비용이 작다는 이유로 낮추지 않는다. "참고"는 어떤 규칙에도 걸리지 않는 개선 제안에만 쓴다.
- 설계 검증: 이슈 #N 본문과 `origin/main...브랜치`의 `docs/architecture.md`·`docs/architecture/`·`docs/changelog.md`·CLAUDE.md diff를 읽는다. 빌드·실행은 하지 않는다. 이슈 본문과 문서가 서로 어긋나면 그 자체로 위반이다. 점검 항목:
  - 이슈의 할 일·완료 조건이 모두 문서로 뒷받침되어, 구현이 문서에 없는 결정을 떠안지 않는가
  - 입력 경계(최소·최대, 빈 값, 형식 오류, 같은 키 여러 개)마다 결과(상태 코드와 ErrorCode, 또는 화면)가 정해져 있는가
  - 외부 호출(다른 서비스·네트워크·파일)이 실패했을 때의 처리(재시도·무시·오류 응답·화면)가 정해져 있는가
  - CI·빌드 환경에 없는 환경변수·백엔드(DB, 외부 API)가 있어도 빌드·테스트가 통과하도록 설계했는가
  - 기존 장(5장 백엔드 규칙, 7장 API 공통 규칙, 9장 에러, 11장 프론트 등)과 CLAUDE.md 규칙에 어긋나지 않는가
  - 완료 조건마다 확인 수단(테스트 또는 화면)이 있고, 그 이슈 범위 안에서 확인할 수 있는가
  - `docs/architecture.md`나 `docs/architecture/`의 장 파일을 바꿨으면 `docs/changelog.md`에 반영했는가
- 구현 검증: 기준(우선순위 순)은 이슈 본문 → 그 브랜치의 `docs/architecture.md`·`docs/architecture/` → 그 브랜치의 CLAUDE.md 규칙. `origin/main...브랜치` diff를 이슈의 할 일·완료 조건·테스트 항목과 하나씩 대조 → `./gradlew build` 직접 실행(프론트 변경 시 lint·typegen·tsc·build·test도, CI 결과는 머지 조건이라 확인하지 않는다) → "통과 / 위반(파일:줄 + 어긴 규칙·문서 위치) / 확인 못 함"으로 정리한다.
- 재검증: 위반을 고친 뒤, 또는 "위반 없음"을 받은 뒤 다시 고쳐서 하는 검증이다. 읽는 범위만 줄이고 판정 기준은 그대로다.
  - 요청에서 받는다: 이전 검증 SHA, 이전 위반 목록(파일:줄과 요지), 이슈 본문에서 바뀐 항목(없으면 "없음"). 위반은 GitHub에 남기지 않아 이슈에서 찾을 수 없으므로 세 가지는 모두 요청에 있어야 한다 (고칠 세션 프롬프트가 이 문구의 틀을 주고, 고칠 세션이 마친 뒤 채운다. 결과 처리). "위반 없음" 뒤에 다시 고친 재검증은 이전 위반 목록이 없고, SHA가 요청에 없으면 이슈에서 같은 단계의 가장 최근 "위반 없음" 결과 코멘트의 SHA를 쓴다.
  - 전체를 읽는 경우(첫 검증과 같다): SHA를 못 구했거나 SHA가 브랜치의 조상이 아닐 때(rebase 등, `git merge-base --is-ancestor`로 확인), 이전 위반 목록 없이 "위반 있음" 뒤의 재검증일 때, 이슈 본문에서 바뀐 항목이 요청에 없을 때(바뀌었는지 알 수 없으므로 아래 이슈 본문 항목을 전부 바뀐 것으로 본다).
  - 읽는다: 이슈 본문 전체, `이전SHA..브랜치` diff, 그 diff가 바꾼 절·파일, diff에서 바뀐 용어·경로·ErrorCode·상수가 다른 곳에 남았는지 `git grep`한 결과, 이전 위반 목록이 가리키는 위치(고쳤는지는 diff가 아니라 현재 파일로 확인한다), 이슈 본문에서 바뀐 항목이 가리키는 장·절(관련 문서). 바뀌지 않은 장·절·파일은 다시 출력하지 않는다. 구현 검증은 수정분과 이전 위반 항목을 이슈의 할 일·완료 조건과 대조하고, `./gradlew build`(와 프론트 검사)는 범위를 줄이지 않고 전부 실행한다.
  - 판정한다: 읽은 범위는 점검 항목 전부와 깐깐한 기준으로 새로 판정하고, 이전의 "통과"를 근거로 쓰지 않는다. 읽지 않은 부분은 이전 검증에서 위반이 없던 범위이면서 이번 수정이 닿지 않은 곳이므로 다시 판정하지 않는다. 이전 위반은 이 예외에 들지 않고 반드시 다시 판정한다. 결과에 이전 SHA와 "읽은 범위: 이전SHA..SHA, 이전 위반 위치, 이슈 본문 변경 항목의 관련 문서. 그 밖은 변경 없음"을 적는다.
- 결과 처리
  - 위반 없음: 사용자 확인 없이 이슈에 코멘트를 남긴다. 제목은 `## 설계 검증 결과` 또는 `## 검증 결과`에 (브랜치, SHA, push 상태, 원격 대비 ahead/behind)를 붙이고, 실행한 검사와 완료 조건 확인을 한 문단으로 쓴 뒤 "위반 없음"으로 맺는다. 필요하면 `### 확인 못 함`, `### 참고`를 덧붙인다. 이어서 단계 라벨을 다음 단계로 바꾼다 (Git 섹션 '라벨').
  - 위반 있음: GitHub에는 남기지 않는다 (바로 고쳐지므로 Public 이슈에는 최종 "위반 없음"만 남긴다). 고칠 세션(설계 검증은 설계 세션, 구현 검증은 구현 세션)에 붙여 넣을 프롬프트를 사용자에게 출력한다. 프롬프트에는 이슈·브랜치·검증 SHA, 위반별 파일:줄·어긴 기준(규칙·문서 위치)·재현·고칠 방향, 마친 뒤 할 일(커밋, 재검증 요청)을 넣는다. 재검증 요청은 새 세션에서 붙여 넣을 문구의 틀로 넣고, 이전 위반 목록은 채워서 준다. 고칠 세션이 마친 뒤 이슈 본문에서 바뀐 항목(없으면 "없음")을 채워 사용자에게 출력한다 (예: `#N 설계 재검증해줘, 이전 검증 SHA: <검증 SHA>, 이전 위반: <파일:줄 요지>, 이슈 본문 변경: <항목 또는 없음>`).
  - 구현 검증에서 설계 결정이 필요한 위반: 설계 세션이 대화 밖에서 읽을 수 있게 이슈에 설계 질문(현상·원인·결정할 선택지)으로 코멘트하고, 구현 세션 프롬프트에는 "설계 결정 후 반영"으로 표시한다. 구현 세션이 같은 내용을 이미 코멘트했으면 다시 남기지 않는다.
