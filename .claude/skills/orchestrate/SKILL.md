이슈 #$ARGUMENTS 를 오케스트레이션한다. 너는 지휘만 한다: 문서·코드를 직접 읽거나 고치지 않고, 각 단계는 Agent 도구로 새 서브에이전트(`verifier`·`reverifier`·`designer`·`implementer`)를 띄운다. 서브에이전트는 빈 컨텍스트로 시작하므로 CLAUDE.md의 "요청 하나에 세션 하나"를 지킨다. 프롬프트에는 아래 문구와 앞 단계가 준 블록만 넣고 네 해석을 덧붙이지 않는다. Agent 호출에 `model`을 지정하지 않는다 (각 에이전트 정의의 모델: `verifier`·`designer`는 opus, `reverifier`·`implementer`는 sonnet). 서브에이전트가 끝났다는 알림을 기다리는 동안 폴링하지 않는다.

이 대화에 설계 등 앞선 내용이 길게 남아 있으면, 시작하기 전에 새 세션에서 `/orchestrate N`을 다시 실행하라고 한 줄 알리고 멈춘다 (앞선 대화가 이후 호출마다 함께 전송되어서).

## 준비
1. `git fetch` 후 `gh issue view N --json title,labels,body`와 대상 브랜치(이슈 본문에 적힌 브랜치, 없으면 `*/#N-*`)를 한 번에 확인한다. 대상 브랜치를 못 찾거나 여럿이면 멈추고 알린다. 단계 라벨이 없으면(설계 전) 멈추고 알린다. 이미 `단계: 설계 검증 통과`면 2단계부터, `단계: 구현 검증 통과`면 4단계만 한다.
   - 브랜치 접두사가 `docs/`(문서·규칙 이슈)면 구현 단계가 없다. 1단계 다음은 4단계이고, `단계: 설계 검증 통과`면 4단계만 한다.
2. 작업 worktree `/home/mini/blog/.claude/worktrees/issue-N`을 쓴다. 없으면 `git worktree add`로 그 브랜치를 체크아웃해 만든다. 원격이 앞서 있으면 그 안에서 pull한다.
   - 브랜치가 저장소 폴더에 체크아웃되어 있으면(설계를 거기서 했을 때) 같은 브랜치를 두 곳에 체크아웃할 수 없다. 저장소 폴더에 커밋하지 않은 변경이 없으면 `git -C /home/mini/blog switch main`으로 옮기고 그렇게 했다고 알린다. 변경이 있으면 멈추고 알린다.
3. `designer`·`implementer` 프롬프트의 첫 줄은 항상 `작업 폴더: /home/mini/blog/.claude/worktrees/issue-N`이다. `verifier`·`reverifier`는 커밋된 브랜치를 자기 worktree에서 보므로 작업 폴더를 주지 않는다.

## 검증 루프 (1·3단계 공통, 고칠 세션 호출 최대 3번)
`<검증 요청>`·`<고칠 세션>`·`<고칠 문구>`는 각 단계에 적힌 값이다.
1. `verifier`에 `검증 세션입니다. <검증 요청>`.
2. 서브에이전트의 마지막 줄로 분기한다.
   - `verifier`의 `판정: 위반 없음` → 루프를 끝내고 다음 단계로. 첫 검증이면 여기서 끝나 재검증·최종 검사를 하지 않는다.
   - `판정: 위반 있음`(누가 냈든) → `<고칠 세션>`에 `<고칠 문구>` + `<fix-prompt>` 내용. `결과: 완료`면 `reverifier`에 `검증 세션입니다. ` + `<reverify>` 내용. `결과: 완료`가 아니면 멈춘다.
   - `reverifier`의 `판정: 판단 불확실` → `verifier`에 `검증 세션입니다. 판단 불확실로 다시 온 재검증이다. ` + 직전 `<reverify>` 내용.
   - `판정: 재검증 통과`(누가 냈든) → `verifier`에 `검증 세션입니다. ` + `<final-check>` 내용 (최종 검사).
   - 그 밖(`설계 결정 필요`·`진행 불가`) → 멈춘다.
3. 고칠 세션을 3번 부른 뒤 재검증이나 최종 검사에서 다시 `위반 있음`이 나오면 멈춘다 (최종 검사의 위반도 라운드에 든다).

## 1. 설계 검증
검증 루프: `<검증 요청>` = `#N 설계 검증해줘`, `<고칠 세션>` = `designer`, `<고칠 문구>` = `설계 세션입니다. 아래 설계 검증 위반을 고쳐줘.`. 끝나면 2단계 (`docs/` 브랜치면 4단계).

## 2. 구현
`implementer`에 `구현 세션입니다. #N 구현해줘`. `결과: 완료`가 아니면 멈춘다.

## 3. 구현 검증
검증 루프: `<검증 요청>` = `#N 검증해줘`, `<고칠 세션>` = `implementer`, `<고칠 문구>` = `구현 세션입니다. 아래 구현 검증 위반을 고쳐줘.`. 고칠 세션이 `설계 충돌`이면 멈춘다. `판정: 설계 결정 필요`면 `<fix-prompt>`가 있어도 멈춘다 (설계가 바뀌면 다시 설계 검증부터 해야 해서). 끝나면 4단계.

## 4. push·PR
작업 worktree에서 브랜치를 push하고 `gh pr create`로 PR을 만든다. 제목은 이슈 제목을 따르는 Conventional Commits 형식(접두사 영어, 제목 한국어), 본문은 `Closes #N`과 커밋 요지 `-` 목록, 마지막 `verifier`가 `화면 확인 필요:` 줄을 줬으면 `## 화면 확인 필요` 절에 그대로 넣는다 (서브에이전트는 화면 확인을 하지 않는다). 머지는 하지 않는다. PR을 만들면 `git worktree remove`로 작업 worktree를 지운다 (브랜치는 남는다).

## 멈출 때와 끝낼 때
사용자에게 짧게 보고한다: 도달한 단계, 라운드 수, 화면 확인 필요 항목(있으면), 마지막 서브에이전트의 판정 줄, 남은 위반 또는 결정할 내용(서브에이전트가 준 블록 그대로), 작업 worktree 경로. 멈출 때는 worktree를 지우지 않는다. 사용자가 결정한 뒤 `/orchestrate N`을 다시 실행하면 단계 라벨로 이어서 시작한다. 위반 내용은 GitHub에 남기지 않는 규칙을 그대로 따른다.
